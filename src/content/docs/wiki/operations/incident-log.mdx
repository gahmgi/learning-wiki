## 2026-11-11 운영서버 용량 초과

- **보인 것**: 오전 10시 20분쯤부터 모든 화면이 504. 그림과 글꼴 같은 정적 파일까지 매번 정확히 10초에 끊겼고, 얼마 뒤 바로 뜨는 503으로 바뀌었습니다. 출근 등록이 몰리는 시간이었습니다.
- **처음 의심**: 일주일 전처럼 무거운 기능 하나가 서버를 붙잡았다.
- **실제 원인**: 운영서버의 용량 초과. 인프라 담당이 서버를 증설해 복구했습니다.
- **알아낸 방법**: 같은 코드가 도는 개발서버는 0.2초에 정상 응답했습니다. 정적 파일까지 정확히 10초라는 점이 「로드밸런서가 서버와 연결을 못 맺으면 10초 뒤 504」라는 AWS 설명과 맞아, 코드보다 서버 쪽을 먼저 묻게 됐습니다. 504가 503으로 바뀐 것은 서버를 빼고 조치하는 중이라는 신호였습니다.
- **다음에는**: 상태 확인 주소와 개발서버를 먼저 비교하고, 서버 쪽이면 재시작 전에 그 시각의 CPU, 메모리, 로그를 받아 두도록 요청합니다.

<Aside type="note" title="아직 모르는 것">
어떤 용량(CPU, 메모리, 디스크, 요금 한도)이 얼마를 넘었는지, 넘기 전에 알려 주는 알람이 있는지, 증설로 얼마나 버틸 수 있는지 설명을 받지 못했습니다. 운영하는 쪽이 이 셋을 모르면 다음에도 장애가 난 뒤에야 알게 됩니다.
</Aside>

## 2026-11-04 요청 하나가 서버를 113초씩 멈춤

- **보인 것**: 관리자가 휴가 관리 화면을 열 때마다 전 직원 화면과 상태 확인 주소까지 502·504가 났습니다.
- **떠올리기 쉬운 것**: 서버가 불안정하다.
- **실제 원인**: 휴가 잔여가 맞는지 점검하는 기능이 재직자마다 결재 파일 전체와 몇 년 치 근태를 통째로 복사해 읽었습니다. 서버 로그에 그 요청이 112,696ms와 112,989ms로 찍혔고, 그 사이 다른 요청 기록은 한 줄도 없었습니다.
- **알아낸 방법**: 서버 로그의 응답 시간. Node.js 서버는 요청을 한 줄로 처리해서, 한 요청이 오래 걸리면 그동안 모두가 기다립니다.
- **고친 뒤**: 필요한 사람 몫만 골라 읽게 바꿔, 운영 규모를 흉내 낸 시험 데이터에서 6,129ms가 398ms로 줄었습니다.
- **다음에는**: 「사람 수만큼 도는 반복 안에서 파일 전체를 읽는가」를 새 기능 검토 항목에 넣습니다. 시험 데이터는 운영 규모로 맞춰야 이런 문제가 미리 보입니다.

## 2026-10-14 고쳤는데 그대로

- **보인 것**: 고쳤다고 알린 화면이 여전히 예전처럼 보였습니다.
- **떠올리기 쉬운 것**: 수정이 틀렸다. 다시 고치자.
- **실제 원인**: 수정은 코드 저장소에 들어가 있었고 내용도 맞았습니다. 운영서버는 그 수정이 들어가기 전 버전이었습니다. 운영서버 배포는 한 사람이 손으로 하고 있었습니다.
- **알아낸 방법**: 상태 확인 주소가 알려 주는 배포 버전과 수정 버전을 비교했습니다.
- **다음에는**: 코드를 다시 고치기 전에 운영서버의 배포 버전부터 봅니다. 「저장소에 반영」과 「운영서버에 배포」를 구분해서 말합니다.

## 2026-10-02 서버 탓인 줄 알았던 실패

- **보인 것**: 새로 만든 기능의 「변경 적용」이 운영서버에서만 실패했습니다.
- **처음 의심**: 서버 환경 문제. 서버 담당에게 확인 요청 문구까지 썼습니다.
- **두 번째 의심**: 다시 보니 우리 코드가 요청마다 파일 상태를 884번 확인하는 비효율이 있었고, 이것을 「유력한 원인」이라고 말했습니다. 그런데 운영서버에서 재 보니 그 요청은 16ms였습니다. 60초 504를 설명할 수 없었습니다.
- **실제 원인**: 기능은 정상이었습니다. 시험한 대상이 관리자 계정이었고, 서버는 설계대로 관리자를 대상에서 거절했습니다. 그 거절 안내가 화면 버그로 지워져 「안 된다」로만 보였습니다.
- **다음에는**: 시험에 쓴 사람과 대상이 거절 규칙에 걸리는지 **운영 데이터로** 먼저 확인합니다. 원인을 확인하기 전에는 「후보 A와 B, 그것을 가를 시험」까지만 말합니다. 추정을 원인처럼 세 번 말했고, 그중 두 번은 실측이 반박했습니다.

## 2026-09-18 갈수록 느려짐

- **보인 것**: 오픈 초기에는 괜찮던 화면이 날이 갈수록 느려졌습니다.
- **떠올리기 쉬운 것**: 사용자가 늘어서.
- **실제 원인**: 요청마다 같은 암호화 열쇠 계산과 같은 파일 읽기를 처음부터 다시 했습니다. 데이터가 쌓일수록 한 번에 드는 비용이 커졌습니다.
- **고친 뒤**: 한 번 계산한 값과 읽은 파일을 기억해 두게 바꿔, 동시 10명 기준 7,521ms가 391ms로 줄었습니다.
- **다음에는**: 「처음엔 빨랐다」는 안심할 근거가 아닙니다. 데이터가 몇 달 쌓인 상태를 가정한 시험을 따로 둡니다.

## 2026-09-16 작업이 날아갔다

- **보인 것**: 화면에서 바꿔 둔 설정과 입력이 갑자기 사라졌습니다.
- **처음 의심**: 누군가 코드를 덮어썼다.
- **실제 원인**: 코드는 한 줄도 사라지지 않았습니다. 개발서버는 코드를 올릴 때마다 새 컨테이너로 다시 떠서 데이터 폴더가 빈 상태로 시작했고, 바꿔 둔 정책은 기본값으로 돌아갔습니다. 백업도 같은 디스크에 있어 함께 사라졌습니다. 그날 10분 사이 코드가 세 번 올라갔고 세 번 모두 같은 효과였습니다. 누구 한 사람의 실수가 아니었습니다.
- **알아낸 방법**: 코드 이력에서 덮어쓰기와 되돌리기가 없는 것을 확인한 뒤, 사라진 것이 코드가 아니라 데이터라는 데서 저장 위치를 의심했습니다.
- **다음에는**: 데이터 저장 위치가 배포와 분리된 디스크인지, 백업이 다른 곳에 있는지를 오픈 전 점검 항목에 넣습니다. 이후 개발서버는 분리된 저장 공간을 쓰도록 바뀌었습니다.
